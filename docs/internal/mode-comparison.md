# モードの比較

現在の配色変換と選択設定の確認結果。方式の説明と内部設定の所在は[アルゴリズム](algorithm.md)、操作と既定値は[使い方](../user/usage.md)を参照。

## 比較条件

Linux 上の Chromium 149.0.7827.55 と Vite 開発サーバーで確認。画像処理はブラウザ内で実行し、外部ホストへのリクエストを遮断した状態でも生成できることを確認している。

元画像は猫のシルエット、等明度の2色領域、および scikit-image のサンプル写真 `astronaut`・`chelsea`・`coffee`。素材は `astronaut`・`coffee`・`chelsea`・`rocket` をそれぞれ5×5に切り出した計100枚とする。比較用に次の素材条件を用意する。

- 色が豊富: 切り出した写真をそのまま使用。
- 青系: 各画素の Oklab 明度を `0.32 + 0.45L`、色味を `a = -0.03, b = -0.10` とした写真。青系に偏る条件を揃えるための人工的な素材である。
- 幅が狭い: 各画素を `L = 0.53 + 0.045L, a = 0.01, b = 0.015` とした写真。明暗と色味がともに乏しい条件を表す。

画質比較は同じ64×64セル、1タイル8px、Oklab、色補正0%、ばらつき0、回転OFF。写真素材の画素変換は検証用であり、アプリが補正0%のアップロード写真を再着色するものではない。

等明度の2色領域は `L = 0.6, a = ±0.1, b = 0` の2色を sRGB へ戻したもの。8 bit 化で生じる微小な明度差だけを増幅して境界を作らないことも確認する。純粋ロジックのテストでは、元画像の赤緑方向の色差を、素材の青黄方向の色差へ置き換える条件も扱う。

## 結果と設定の根拠

境界の補助指標は「元画像で隣接セルの Oklab 距離が0.08を超える箇所のうち、選んだ素材の距離が0.025を超える割合」とする。タイルの平均色から算出する指標であり、被写体の認識率や写真内部の輪郭の評価ではない。

| 元画像 / 素材          | 色を優先 | バランス | 形を優先 | 全体表示での確認                                       |
| ---------------------- | -------: | -------: | -------: | ------------------------------------------------------ |
| 猫シルエット / 青系    |    80.7% |    92.4% |     100% | 紺色の猫と明るい青の背景で輪郭を区別できる             |
| 等明度の2色領域 / 青系 |       0% |     100% |     100% | 色優先ではほぼ同じ青になる。適応モードでは濃淡を分ける |
| 人物 / 色が豊富        |    94.0% |    96.9% |    99.1% | 色優先の色再現が最も近く、形優先では配色変更も大きい   |
| 猫の写真 / 青系        |    96.3% |    98.7% |    99.7% | 顔の輪郭と陰影を青系の配色で表現できる                 |
| コーヒー / 幅が狭い    |    32.7% |    32.0% |     0.1% | 全モードで低コントラスト。形優先も改善を保証しない     |

明暗の範囲だけを合わせ、色味の差を配色へ反映しない比較方式では、等明度の2色領域の境界は残らない。色味の差を素材の色差や明暗へ対応させる処理が必要になる。

人物と色が豊富な素材の組み合わせで、元色への平均 Oklab 距離は色優先0.0529、バランス0.0756、形優先0.1105。バランスは配色変更を部分的に許す設定とし、元の色の印象を残す位置付けにする。

隣接関係の重みは0・0.7・2・4を比較した。人物の境界指標は順に98.7%・98.9%・99.1%・99.1%で、強い重みの改善は小さい。形優先は元色からの追加の乖離を抑える側の設定を採用し、バランスは関係評価を弱める。これらの値は代表例での調整結果であり、全画像に対する最適値ではない。

拡大表示では、補正0%は選んだ写真の縮小後の色を保ち、補正35%では写真の色味が変わることを確認している。全体の境界が改善しても、1枚の写真の細部はタイル解像度に制約される。小さなタイルを表示倍率だけで拡大しても、失われた細部は復元しない。素材の明暗・色味が狭い場合や強い補正で画素値が飽和する場合は、全体と写真の両方が見やすくなるとは限らない。

## 処理時間とメモリ

元画像はサンプル写真を4,000×3,000pxへ拡大した12MP相当の画像。素材は256pxで保持する。300枚の条件は切り出し写真の反復を含み、独立した300色を持つ素材の負荷を示すものではない。

以下は1回の実行で測った概数。時間は Worker 内の配色・配置・描画・JPGエンコードを含み、Workerへ渡す素材のコピー作成を含まない。解析は生成前に1回行い、各モードで再利用する。

| 素材数 / グリッド / 出力        | 解析 | 色優先 | バランス | 形優先 |
| ------------------------------- | ---: | -----: | -------: | -----: |
| 100枚 / 128×96 / 3,072×2,304px  | 56ms |  130ms |    155ms |  151ms |
| 300枚 / 256×192 / 4,096×3,072px | 34ms |  382ms |    394ms |  380ms |

上表は補正0%・ばらつき0・回転OFF。補正35%・ばらつき0.01・回転ONでは、100枚で210〜271ms、300枚で565〜622msだった。いずれも Oklab を選択している。JITコンパイルやキャッシュの影響を含むため、素材数による単純な増減や端末間の性能差はこの表から判断できない。

メモリは Chromium の renderer プロセスの RSS 合計を50ms間隔で取得した。100枚では生成前313MiB・観測最大415MiB、300枚では生成前432MiB・観測最大542MiB。ブラウザの内部領域や共有ページを含み、短いピークを取り逃す可能性がある。アプリの純粋な追加使用量や iOS の必要メモリを示す値ではない。

## ブラウザ確認と未確認項目

Chromium の1,280px幅と390px幅で次の動作を確認済み。

- RGB／Oklab と全3モード、通常生成と3モード比較。
- 色補正・ばらつき・回転の併用、JPG／PNG、表示中の結果のダウンロードと使用箇所のハイライト。
- 比較内で同じ seed を使い、切替時に表示倍率とスクロール位置を保つこと。
- 元画像・素材・グリッドの変更による解析更新と、古い結果の破棄。素材1枚での解析と注意表示。
- 全6組み合わせについて、単色素材の補正0%では出力画素が選択素材の色と一致し、補正100%では各モードの目標色と一致すること。
- 解析の世代が異なる Worker リクエストを拒否すること。

**iOS Safari 実機、Firefox、Safari デスクトップは未確認。** iOS 実機では、素材の分割追加、3モード比較の繰り返し、拡大・切替、JPG／PNGの保存、端末上限付近での生成を確認する必要がある。390px幅の Chromium 確認は iOS のメモリ・キャンバス制約の代わりにはならない。
